# Local operations runbook — not staging deployment
1. Run the complete CI on the release commit. No rollout until CI succeeds and human security review is recorded.
2. Start the local server; GET /healthz must return 200 with status ok. It tests SQLite availability, not model availability. A local monitoring process may poll it. Configure external alert delivery only after choosing the staging host.
3. Create a consistent private snapshot: python tools/backup_orbit.py backup company.sqlite snapshot.sqlite. Restore to a new file: python tools/backup_orbit.py restore snapshot.sqlite restored.sqlite. Test a local instance using AI_COMPANY_DB=restored.sqlite on a different port; sessions are invalidated. Keep backups off-host encrypted and test recovery time.
4. Rollback: stop writes and stop service, retain current database and logs, restore a tested compatible snapshot into a new file, restart the previously accepted commit using that file, reauthenticate, run smoke checks and reconcile lost writes. Do not overwrite live data. Actual rollback drill and recovery objectives must be measured in staging.
5. Real model workflow: run the preflight then explicit model calls; inspect reviews and model outputs, run the explicit Docker-only verification CLI, obtain Tech Lead selection, then dry-run publication. Do not enable GitHub writes by default.
6. Staging still requires target infrastructure, TLS and secure-cookie/proxy configuration, production-grade authentication/abuse protection, monitoring and alerting, secret management, isolated test data, security review and UAT. The current server refuses non-loopback bind. Do not publish this MVP directly.
7. Owner records evidence in /access.html; only after all criteria pass can the owner sign off. CI and evidence references are not external deployment. Mobile remains out of scope.
