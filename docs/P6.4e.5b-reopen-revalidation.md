# P6.4e.5b — Explicit reopen and retest revalidation

REOPEN is an explicit approve-scoped command on a CLOSED occurrence, using the existing exact current view digest, registration digest and action confirmation. It appends an ASSIGNED receipt with the original assignee and no active repair evidence. The prior CLOSE remains immutable. If the assignee is no longer authorized, a reviewer must reassign before START. The current authoritative registry must be READY; missing, corrupt or stale evidence still blocks mutation.

Every occurrence (including historical ones) is addressable by exact finding ID and registration digest. The original registration for SUBMIT/VERIFY/CLOSE is selected by that digest, not the latest finding. Historical closures do not resolve other occurrences.

After reopening, submission, verification and closure require a trusted execution strictly later in the immutable assertion-run chain than the last closure's execution. The same run or unknown/older run is rejected. A new run may already exist when REOPEN is issued; no automatic execution occurs. VERIFY/CLOSE retain the unchanged full-regression and original-assertion checks, and independent reviewer requirements. A current closure may also be explicitly reopened, but cannot be reclosed using its old execution. Existing history schemas and prior receipts are unchanged.

The current read-only Retest Quality Gate still requires every occurrence's explicit current closure. UI changes and mandatory Docker retest acceptance remain subsequent increments. Unit regressions exercise the state machine, exact historical binding, freshness, RBAC, duplicate rejection and atomic rollback. No release, merge, model or execution authority.
