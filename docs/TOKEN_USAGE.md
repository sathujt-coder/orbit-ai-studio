# P5.1 — Token Usage Tracking
The server records a durable per-attempt ledger for pipeline drafts/reviews/synthesis, coding proposals/reviews including format retries, agent chat and explicit provider probes. Every call commits a pending row before transport, then records response status, latency, exact reported token counters, provider/model, agent, project, purpose and run ID. No prompts, responses, keys, URLs or raw provider errors in the ledger. Demo calls produce no ledger entries. A process crash can leave pending rows; they represent uncertain attempts, not free calls. SQLite write failures fail closed, without automatically replaying model requests.

Ollama native prompt_eval_count/eval_count and OpenAI-compatible usage.prompt_tokens/completion_tokens/total_tokens are normalized. Missing counts are NULL; partial and inconsistent responses have separate coverage states. Known subtotals are not full consumption or invoices. Counts reflect provider reporting, not a verified tokenizer, and failed output can consume tokens. Provider model discovery is not inference. Project members may read their project usage; the global summary including system probes is operator-only.

Dashboard /usage.html offers 1/7/30/90-day UTC views, input/output/known totals, request and coverage counts, daily and grouped agent/model/purpose data. No automatic refresh, no cost estimates or budget enforcement yet. CLI tools other than the instrumented offline smoke are not covered by the web ledger. The offline smoke records actual generation/review/repair calls (not its pre-DB connectivity probe) and requires complete native token evidence on successful rounds. CI covers both real model reports and fixture/browser tests. Production persistence, retention, billing reconciliation, budgeting and load testing remain future work.
